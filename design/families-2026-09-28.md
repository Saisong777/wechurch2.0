# 我的小家：加入、互動與牧養管理

## Scope and design

Sai approved the preceding group workflow and requested implementation with the
member-facing name changed to 小家. This is a scoped product change, reusing the
approved WeChurch Together tokens, header and login. No global visual redesign,
new navigation bar, dependency installation, external notifications or A release.
Existing group IDs/routes/table names and user-authored content are preserved.
Game/activity 分組 is a different concept and is not renamed.

Before: /groups offered an invitation token field, managed memberships and four
separate reading/note/prayer/care tabs. There was no newcomer matching intake or
publicly opted-in family directory. CRM had basic creation/assignment, without a
member-facing matching handoff or audited atomic transfers.

After: /groups offers three entry paths; each family defaults to a chronological
feed with note/prayer/message filters, reading and information tabs. Sharing is
inline with explicit consent. Existing comments, prayed reactions, answered
prayers and shared care remain available. Information exposes membership and
care; managed settings are also reachable through CRM's 小家 tab.

## Delivered contracts

- Matching requests require church, availability, contact and explicit consent.
  One active request per member; requester can inspect progress or cancel.
- Directory contains only opt-in active families: name, church, public description
  and public meeting summary. No membership roster or private announcement.
- Matching enters a leader-confirmed join request, not automatic content access.
- Invitations retain existing long URLs and add 12 hex digits formatted in three
  groups plus locally generated QR. Seven-day expiry, hashed storage, rotation
  revocation and per-identity join rate limits; old long URLs remain supported.
- Ordinary member posts and existing Bible/prayer excerpts share one feed and
  reply mechanism. Personal sources and public walls are separate.
- Management scope follows existing church/group capability assignments. New
  families require church-level member-management scope; a future-leader role
  alone does not grant it. Designated family leaders manage their own family.
- Settings include opt-in directory, meeting summary, private announcement,
  active/paused/archive state and church-authorized leadership handover.
- Pausing revokes invitations and stops intake. Archiving requires member
  transfers/removals first and removes member-facing access, not personal data.
- Transfers lock source/destination in stable order, require both scopes, record
  history and remove old membership/watch access. Shared care assignments are
  released. Other memberships, personal notes and accounts are untouched.
- New memberships see shares/care created after joining; old memberships retain
  their existing access via an epoch cutoff. Direct comment/care endpoints enforce
  the same boundary. Designated leaders can access family history. This does not
  grant global administrators access to private member-facing posts.

## Migration and rollback

0016_families is additive except for expanding the share kind check. No user
records are deleted or membership names rewritten. Back up B before migration;
application DB permissions must cover the two new tables. Retain the migration
on app rollback; old applications do not understand message posts, so retain the
new release or disable message creation while preparing a forward fix. Never
reverse migration by deleting family data. A is unchanged.

## First use

Members open `/groups`: request assistance, select an opted-in family, or enter
an invitation code. Scan an invitation QR with the phone's normal camera.
All three routes require leader confirmation before family content is available.
Existing families are private/unlisted by default; authorized coworkers enable
the directory through `/groups?manage=1` or CRM's 小家 tab. Do not bulk-open them.

## Deliberately not claimed complete

Notification delivery/digests, account-bound one-time invitation acceptance,
primary-home vs course-group classification, a separate church-departure workflow
and automatic reading check-in integration are follow-up phases. Existing
confidential pastoral case workflows remain separate from all-member shared care.
This release is not iPhone hardware acceptance or large-concurrency certification.
